# 一斉（仮称）

メイン画面1つと参加者のスマホで遊ぶ、5〜30人のパーティゲーム。
これは**ミニゲーム2本を実装した検証用プロトタイプ**で、
設計全体が乗っている前提——「端末のタイムスタンプで判定すれば通信の遅延は
結果に効かない」——を実機で確かめるために作った。

## 動かす

```
node issei/server.js
```

起動すると2つの URL が出る。

- **メイン画面**（プロジェクターに繋いだPC）… `http://localhost:3000/screen.html`
- **スマホ**（同じ Wi-Fi から）… `http://<表示されたIP>:3000/phone.html`

名前を入れて参加し、メイン画面で **SPACE** を押すと始まる。2本がランダムな順で回る。

- **せーの** … 4拍の予告のあと、全員が同じ瞬間にボタンを押す。ばらつき 80ms 以内で全員成功
- **だるまさんがころんだ** … 押している間だけ前進。鬼が振り向いた瞬間に押していたら脱落

アプリのインストールは不要。クラウドも不要。ホストのPCがそのままサーバーになる。

## 検証する

```
node issei/test-latency.js    遅延を注入しても結果が変わらないことを確認
node issei/test-ui.js         実ブラウザで参加〜結果まで通す（撮影付き）
```

`test-latency.js` は、片道 2ms から 200ms までのばらばらな回線と、
ばらばらな時計のズレを持つ仮想プレイヤー6人を作り、全員が「狙った腕前ちょうど」に
押したときサーバーの判定がそれと一致するかを見る。

現在の実測:

```
最大の判定ズレ  2.0ms   (許容 15ms)
帯の一致      6 / 6人
遅延の効き方    遅延+100ms あたり 0.44ms ずれる  (許容 3ms)
区間の組み直し: 全員一致
```

**0.44ms / 100ms** が本命の数字。回線が 100ms 遅くなっても判定は 0.44ms しか動かない、
つまり順位が腕前だけで決まっていることを意味する。

だるまさん側は、押下イベントを**わざと順不同・ばらばらの遅延で送って**も、
サーバーが時刻で組み直して同じ判定に到達することを確認している。

## 分かったこと

限界は通信の遅延ではなく**時計合わせの精度**だった。同じ部屋の同じ Wi-Fi なら
片道は数 ms なので実用上は問題ない。

推定を「速かった標本を選ぶ」方式から「各標本が与える区間を全部重ねる」方式に
変えたところ、片道 200ms での誤差が 12.5ms → 2.7ms に改善した。
さらに起動時の 20 標本に加えて、遊んでいる間も裏で測り足して精度を上げ続ける。

検証を書くときの落とし穴も1つ見つけた。仮想プレイヤーが押す瞬間を「自分の合わせた時計」で
決めると、時計合わせの誤差が往復で相殺されて**テストが甘くなり、嘘の PASS が出る**。
人間はメイン画面を見て押すのだから、実時刻で決めないといけない。
