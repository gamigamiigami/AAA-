# 一斉 — 技術仕様

メイン画面1つと参加者のスマホで遊ぶ、5〜30人のパーティゲーム。
これはその技術側の契約書。ゲーム内容の設計は別途まとめてある。

---

## 0. この設計の一点

**判定は「パケットが届いた時刻」ではなく「端末が押した時刻」で行う。**

ここだけが全体を支えている。これが成り立つなら以下が全部ついてくる。

- 回線の速さが勝敗に影響しない
- 低遅延の伝送路が要らない（WebSocket 不要）
- スマホの描画性能が結果に無関係になる
- サーバーは1台のノートPCで足りる

逆にここが崩れると、他の工夫では取り返せない。
だから `test-latency.js` で機械的に検証している。

---

## 1. 構成

```
issei/
  server.js           依存ゼロの HTTP サーバー。部屋の状態と判定を持つ
  public/
    common.js         時計合わせ・通信・識別・散布軸（両画面が読む）
    screen.html       メイン画面（プロジェクター）
    phone.html        スマホ（コントローラ）
  test-latency.js     遅延公平性の検証
  test-ui.js          実ブラウザでの煙テスト
```

依存パッケージなし。Node の標準機能だけで動く（テストのみ playwright を使う）。

---

## 2. 伝送路

**SSE（サーバー→全員）+ POST（各自→サーバー）。WebSocket は使わない。**

性能を諦めたのではない。判定が押下時刻で行われる以上、伝送が 50ms でも
500ms でも結果が 1ms も変わらないため、低遅延の伝送路そのものが不要になる。
SSE は HTTP のままなので、プロキシや社内ネットワークも通りやすい。

| 経路 | 用途 |
|---|---|
| `GET /api/events` (SSE) | 部屋の状態を全員へ配信 |
| `GET /api/time` | 時計合わせ。何度も叩かれる |
| `GET /api/state` | 現在の状態（デバッグ・テスト用） |
| `POST /api/join` | 参加。id と見た目が返る |
| `POST /api/press` | 押下。**中身の `at` だけを見る** |
| `POST /api/start` `/api/stop` | 進行制御 |

## 3. 時計合わせ

NTP と同じ考え方。

```
t0 = 端末の時刻
      → サーバーが t1 を返す →
t2 = 端末の時刻

rtt    = t2 - t0
offset = t1 - (t0 + t2) / 2      // serverTime = localTime + offset
```

各標本は offset の取りうる**区間**を1つ与える。

```
t1 = t0 + d1 + offset   (d1 >= 0)  →  offset <= t1 - t0
t2 = t1 + d2 - offset   (d2 >= 0)  →  offset >= t1 - t2
```

つまり `offset ∈ [t1-t2, t1-t0]`。**全標本の区間を重ね合わせて絞り込む**（NTP と同じ区間交差）。
標本を選んで平均する方式より原理的に狭くなる。実測でも片道 200ms の誤差が
12.5ms → 2.7ms に改善した。区間が交わらない場合だけ最小 RTT の標本に頼る。

**起動時に 20 標本**、その後は**遊んでいる間に 4 秒ごとに 1 標本ずつ測り足す**。
遅い回線ほど標本が要るが、起動時に何十回も測ると待たせてしまうため、
精度は時間をかけて上げる。12 分のセッションなら数百標本たまる。

### 実測した精度（`test-latency.js`）

| 片道遅延 | 時計合わせ誤差 |
|---:|---:|
| 2ms | 0.2ms |
| 12ms | 0.0ms |
| 35ms | 0.5ms |
| 80ms | 0.5ms |
| 150ms | 2.2ms |
| 200ms | 2.7ms |

**時計合わせの誤差が、この設計の本当の限界**である。通信の遅延そのものではない。
片道 200ms までは判定ズレが 3ms 以内に収まり、これは人間の反応時間の個人差
（数十 ms）に十分埋もれる。片道 400ms（衛星級）まで行くと誤差が判定に見え始める。

同じ部屋の同じ Wi-Fi という想定なら片道は数 ms なので、実用上の問題はない。

## 4. 押下の扱い

```js
// スマホ側
const local = ev.timeStamp;           // イベントが発生した時刻。
                                      // JS が処理した時刻ではないので、
                                      // メインスレッドが詰まっても取り逃さない
const at = local + GG.clock.offset;   // サーバー時計に変換
post('/api/press', { id, at });       // 届くまでの時間は判定に無関係
```

```js
// サーバー側
error = at - target;                  // 到着時刻は一切参照しない
```

**手応えはサーバーの返事を待たずにその場で返す**（色 + 振動）。
人間は「押した瞬間に反応した」としか感じない。ここが体感の分かれ目。

---

## 5. 判定の粒度

**ms の生ランキングをしない。帯で判定する。**

| 帯 | 範囲 |
|---|---|
| PERFECT | ±80ms |
| GREAT | ±160ms |
| GOOD | ±260ms |
| MISS | それ以上 |

理由は2つある。端末のタッチ読み取り遅延に数十 ms の機種差があり、これは
JS から測れない。そして腕前が数 ms しか違わない2人は、どんな仕組みでも
測り分けられない。帯にすれば端末差が結果をひっくり返さなくなり、
同点を許すことで気持ちよさも上がる。

## 6. 画面とスマホの役割

| | 担当 |
|---|---|
| **メイン画面** | 音・ドラマ・結果・順位。全員の識別、残り時間、生存数 |
| **スマホ** | 自分の形と色、ボタン、触覚 |

- **音は必ずメイン画面から。** 30 台から音を出すと濁るうえ同期できない。
  1台のスピーカーから全員に同時に届く、この形式で最も速く公平な情報路。
- **スマホは主画面を映さない。** ミニチュアを出すと全員が下を向いて共有体験が死ぬ。
  位置を答えるゲームでは、主画面に格子ラベルを描き、スマホはラベルのキーパッドだけ持つ。
- **入力中は「何人送信済み」だけ出す。** 誰が速かったかを出した瞬間に遅延が
  可視化されて不公平になる。

## 7. 識別

30 色は識別できない。**形が主・色が従**とする（色覚多様性にも効く）。

10 形 × 4 色 = 40 通り。ただし形を一巡してから色を変えると最初の 10 人が
全員同色になり、少人数のとき色が役に立たない。隣り合う人が形も色も変わるよう配る。

```js
shape = SHAPES[i % 10];
color = COLORS[(i + Math.floor(i / 10)) % 4];
```

## 8. 共通部品

`GG.scatter()` — ズレを競う全ゲーム（せーの・ピタリ・体内時計）で使い回す散布軸。
ゲーム本体より、この一枚の絵の方が体験の本体になる。近い点は自動で縦に積んで
30 人でも潰れないようにしてある。

## 9. 運用

会場は一部屋なので、**ホストの PC がサーバーになり、全員が同じ Wi-Fi で繋ぐ**。
クラウドは要らない。

```
node issei/server.js
```

起動すると LAN の IP が表示される。参加者はそこへブラウザで来るだけ
（アプリのインストールなし）。30 人に URL を打たせると 3 分溶けるので、
本番では主画面に QR コードを出すこと。

### 既知の制約

- **iOS では傾き・シェイクに HTTPS が要る。** LAN の HTTP では
  `DeviceMotionEvent` が使えないため、体動系を入れる段階で自己署名証明書か
  トンネルが必要になる。ボタンだけのゲームは HTTP のままで動く。
- **会場によっては AP のクライアント分離**で端末から PC に到達できない。
  その場合はホストがテザリングを張る。
- 部屋は1つだけ。複数同時開催は未対応。

## 10. ミニゲーム

`games.js` に1本1オブジェクトで置く。サーバーは中身を知らない。

| 必須 | 役割 |
|---|---|
| `setup(now, rng)` | その回の状態を作る。`endsAt` を必ず返す |
| `accept(g, id, ev)` | 入力を受ける。**時刻は中身から取り、到着時刻は見ない** |
| `judge(g, players)` | `{entries, winners}` を返す |

`rng` はシード付き（mulberry32）。`Math.random()` を直に使ってはならない。同じ種なら同じ試合が再現できる。

実装済みは2本。

- **せーの** … `tap`。全員のばらつきが 80ms 以内なら全員成功（協力）
- **だるまさんがころんだ** … `hold`。押し始めと離した瞬間を時刻付きで送り、
  サーバーが押下区間を組み直して、監視窓と重なったら脱落。
  **イベントは順不同で届いてよい**（時刻で並べ直すため）。表示は遅れてもよいが判定は狂わない

出題順はランダム。同系統が続く回も出るが、まずそのまま回して様子を見る方針。

### 調整で分かったこと

だるまさんのゴールを近く置くと、危険を冒す理由がなくなって全員が余裕で完走し、
駆け引きが消えた（6人中5人がゴール）。**ゴールは「安全に稼げる時間」より遠くに置く**
必要がある。掛け声から安全に取れるのが合計12秒ほどなので、必要8秒に設定した。

## 11. 検証

```
node issei/test-latency.js    遅延公平性（機械判定）
node issei/test-ui.js         実ブラウザでの通し（スクリーンショット付き）
```

`test-latency.js` の合格条件は3つ。

1. 判定ズレが全員 15ms 以内
2. 帯の判定が全員一致
3. **遅延が 100ms 増えたときの判定ズレの増分が 3ms 未満**
4. だるまさんの押下区間が、順不同で届いても全員正しく組み直せる

3 が本質だが、当初は相関係数で見ていて失敗した。判定ズレが `0, 0, 0, -1, +3` ms の
ような**ほぼゼロのデータでも相関は簡単に 0.5 を超える**——丸め誤差を見ているだけで、
大きさの情報がない。「遅延 +100ms あたり何 ms ずれるか」という傾きに変えると
大きさを持つ指標になる。現在の実測は **0.44ms / 100ms**。

なお検証を書くときは、仮想プレイヤーが押す瞬間を**実時刻**で決めること。
自分の推定時計で決めると、時計合わせの誤差が往復で相殺されてテストが甘くなる
（実際に一度これで誤った PASS を出した）。人間はメイン画面を見て押すのであって、
自分のスマホの時計合わせの結果を見て押すわけではない。
