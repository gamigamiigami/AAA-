# 一斉（仮称）

メイン画面1つと参加者のスマホで遊ぶ、5〜30人のパーティゲーム。
これは**ミニゲーム2本を実装した検証用プロトタイプ**で、
設計全体が乗っている前提——「端末のタイムスタンプで判定すれば通信の遅延は
結果に効かない」——を実機で確かめるために作った。

## 動かす

```
node issei/server.js
```

起動すると2つの URL が出る。

- **メイン画面**（プロジェクターに繋いだPC）… `http://localhost:3000/screen.html`
- **スマホ**（同じ Wi-Fi から）… `http://<表示されたIP>:3000/phone.html`

名前を入れて参加し、メイン画面で **SPACE** を押すと始まる。2本がランダムな順で回る。

- **せーの** … 4拍の予告のあと、全員が同じ瞬間にボタンを押す。ばらつき 80ms 以内で全員成功
- **だるまさんがころんだ** … 押している間だけ前進。鬼が振り向いた瞬間に押していたら脱落

アプリのインストールは不要。クラウドも不要。ホストのPCがそのままサーバーになる。

## 検証する

```
node issei/test-latency.js    遅延を注入しても結果が変わらないことを確認
node issei/test-ui.js         実ブラウザで参加〜結果まで通す（撮影付き）
node issei/test-sound.js      実ブラウザで鳴らして解析器で測る
```

`test-latency.js` は、片道 2ms から 200ms までのばらばらな回線と、
ばらばらな時計のズレを持つ仮想プレイヤー6人を作り、全員が「狙った腕前ちょうど」に
押したときサーバーの判定がそれと一致するかを見る。

現在の実測:

```
最大の判定ズレ  2.0ms   (許容 15ms)
帯の一致      6 / 6人
遅延の効き方    遅延+100ms あたり 0.44ms ずれる  (許容 3ms)
区間の組み直し: 全員一致
```

**0.44ms / 100ms** が本命の数字。回線が 100ms 遅くなっても判定は 0.44ms しか動かない、
つまり順位が腕前だけで決まっていることを意味する。

だるまさん側は、押下イベントを**わざと順不同・ばらばらの遅延で送って**も、
サーバーが時刻で組み直して同じ判定に到達することを確認している。

## 分かったこと

限界は通信の遅延ではなく**時計合わせの精度**だった。同じ部屋の同じ Wi-Fi なら
片道は数 ms なので実用上は問題ない。

推定を「速かった標本を選ぶ」方式から「各標本が与える区間を全部重ねる」方式に
変えたところ、片道 200ms での誤差が 12.5ms → 2.7ms に改善した。
さらに起動時の 20 標本に加えて、遊んでいる間も裏で測り足して精度を上げ続ける。

検証を書くときの落とし穴も1つ見つけた。仮想プレイヤーが押す瞬間を「自分の合わせた時計」で
決めると、時計合わせの誤差が往復で相殺されて**テストが甘くなり、嘘の PASS が出る**。
人間はメイン画面を見て押すのだから、実時刻で決めないといけない。

詳しくは [ARCHITECTURE.md](ARCHITECTURE.md)。

## 見た目と音

描画は `public/art.js`（部品）と `public/stage.js`（画面）の2枚。
デモ（1台完結）と本番（サーバー接続）が同じ `stage.js` を使う。
描画を二重に持つと必ず片方が古くなるので、ここは1つに束ねてある。

守っている原則:

- **光源はひとつ**。`Art.LIGHT` から、胴の明暗・リムライト・落ち影の向きを引く。
  吊り物は `Art.RIG` から、器具・ビーム・床の光だまりを引く。
  光っている物と照らされている物が無関係な画面は、必ず書き割りに見える。
- **消失点もひとつ**。`Art.horizon()` から、床の板もキャラの大きさも引く。
  手打ちの表にすると、床とキャラが別の地平線を持ってずれる（実際 125px ずれていた）。
- **形が主、色が従**。30色は見分けられないので、体型10種・頭の飾り・顔つきで分ける。
  20px の黒い塊だけで判別できることを、縮小して目で確かめてある。
- **金はロゴだけ**。「いま操作する場所」は白。装飾は必ず見出しより奥。

音は `public/sound.js`。素材ファイルは使わず合成する。効果音は必ず層
（ノイズの立ち上がり＋音程のある胴体＋ピッチの動き）で組む。
曲は場面で3層に切り替え、**「せーの！」の直前は完全に無音にする**。
無音がいちばん強い緊張装置で、しかも一銭もかからない。

## 画面を確かめる

コードを読んで「良くなったはず」で終わらせないこと。必ず描いて見る。

```
node issei/test-ui.js          本番画面のスクショが issei/shots/ に出る
```

デモ画面には撮影用のフラグがある。

- `demo.html?card=1` … 命令カードを出したまま止める
- `demo.html?win=1`  … 必ず成功させる（紙吹雪と歓喜の画面を撮るため）

`?win=1` は後から足した。それまで勝利画面は一度もスクリーンショットに
写っておらず、ゲームでいちばん華やかな1枚を「たぶん大丈夫」で済ませていた。
撮れない画面は直っていないのと同じ。

## 作りながら踏んだ穴

同じ失敗を繰り返さないために残しておく。

- **コメントに書いて実装しない。** 「板ごとに幅を変える」「鬼は逆光のシルエット」と
  書いて、どちらも実装していなかった。設計理由を書いた場所は、次の読み手が
  真っ先に検証する場所。そこで嘘が出ると他の判断まで疑われる。
- **数値を見えない値まで下げる。** 床が白飛びしたので光だまりを薄くしたら、
  床の木目の縞より弱くなって完全に不可視になっていた。いまは下限を置いてある。
- **作り分けを後段の共通化で潰す。** 体型10種・顔10種・腕5種を作ったのに、
  腕の左右対称1行と口幅の共通化で全部相殺されていた。
  テーブルを増やすより、後段の共通化を外すほうが効く。
- **小さい絵で確認を済ませる。** 腕の付け根が胴の奥に埋まっていたのを、
  小さい一覧で見て「付いた」と判断していた。1体を大きく描いたら一目だった。
- **指摘を確かめずに直す。** 受けた指摘のうち3件は、検算・実測したら誤りだった。
  確かめずに直していたら画面が悪くなっていた。
