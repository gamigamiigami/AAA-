# 一斉（仮称）

メイン画面1つと参加者のスマホで遊ぶ、5〜30人のパーティゲーム。
これは**「せーの」1本だけを実装した検証用プロトタイプ**で、
設計全体が乗っている前提——「端末のタイムスタンプで判定すれば通信の遅延は
結果に効かない」——を実機で確かめるために作った。

## 動かす

```
node issei/server.js
```

起動すると2つの URL が出る。

- **メイン画面**（プロジェクターに繋いだPC）… `http://localhost:3000/screen.html`
- **スマホ**（同じ Wi-Fi から）… `http://<表示されたIP>:3000/phone.html`

名前を入れて参加し、メイン画面で **SPACE** を押すと始まる。
4拍の予告のあと、全員が同じ瞬間にボタンを押す。ばらつきが 80ms 以内なら全員成功。

アプリのインストールは不要。クラウドも不要。ホストのPCがそのままサーバーになる。

## 検証する

```
node issei/test-latency.js    遅延を注入しても結果が変わらないことを確認
node issei/test-ui.js         実ブラウザで参加〜結果まで通す（撮影付き）
```

`test-latency.js` は、片道 2ms から 200ms までのばらばらな回線と、
ばらばらな時計のズレを持つ仮想プレイヤー6人を作り、全員が「狙った腕前ちょうど」に
押したときサーバーの判定がそれと一致するかを見る。

現在の実測:

```
最大の判定ズレ  6.0ms   (許容 15ms)
帯の一致      6 / 6人
遅延との相関   -0.08   (0 に近いほど、回線が結果に漏れていない)
```

**相関 −0.08** が本命の数字。回線の速さと判定の狂いに関係がない、
つまり順位が腕前だけで決まっていることを意味する。

## 分かったこと

限界は通信の遅延ではなく**時計合わせの精度**だった。片道 200ms までは
判定ズレが 6ms 以内に収まるが、400ms（衛星級）では 30ms に悪化する。
同じ部屋の同じ Wi-Fi なら片道は数 ms なので実用上は問題ない。

対策として、起動時に 20 標本を取ったあと、遊んでいる間も裏で測り足して
精度を上げ続けるようにしてある。
